# 子代理隔离边界 · 决策材料

> 用途：安全票（子代理隔离边界）的**拍板材料**。三个子问题各自给出「现状（附证据）/ 选项 / 影响」。
> 本文件**不给结论**——结论由用户拍板。文末给出实施方建议（明确标注为建议）。
> 日期：2026-09-19　相关：`docs/design/tool-linkage-laws.md`、研究报告 §3.2 实施核对项 E2

---

## 0. 共同根因（三个子问题其实是**同一个**设计问题）

子代理的 loop 不是"父 loop 的子集"，而是**另起一个 `AgentLoop`**：
`delegate-tool.ts:318` `new AgentLoop({...})`，未注入 `pluginHost` / `loopHooks`
⇒ `create-kernel` 给它造**全新空宿主 + 空钩子总线**。

**后果（一条链）**：任何"挂在父 loop 上的东西"都不会跟过去 ——
插件钩子（含权限链）✗、宿主服务（含 xref 能力）✗、权限门 ✗。
于是三个子问题的答案目前都是"不跟过去"，而**替代防线只有两道**：
工具白名单（`delegate-tool.ts:243` `FilteredToolRegistry(parent, allowedTools)`）
+ 路径沙箱（`:246-249` `createSandboxedTool(tool, sandboxRoot)`，**仅当 `sandboxRoot` 被设置**）。

## 1. 钩子：子代理的 loop 要不要接插件钩子？

**现状（证据）**
- 子代理 loop 未注入 `pluginHost`/`hooks`（`delegate-tool.ts:318-336`）⇒ 空总线。
- 权限链插件的挂载面**明写**是主循环总线：`plugins/permission-chain.ts:4`「挂载面：主循环钩子总线」；
  装配处在 `gateway/agent-assembly.ts:463-464`（内核基座插件）。
- ⇒ 子代理内的工具执行**不经权限链**；而它的 `onPermissionRequest` 又恒答 `'yes'`
  （`delegate-tool.ts:314` 注释：「子 Agent 自动批准权限请求」）⇒ **双重绕过**。

**选项**
| | 做法 | 代价 |
|---|---|---|
| A（现状）| 保持不接 | 隔离干净、插件作者不必考虑"在子代理里也跑"；代价：子代理内没有权限门/写护栏，全靠白名单+沙箱 |
| B | 共享父总线（钩子全量透传）| 一处挂载处处生效；代价：插件行为在子代理里被**放大**，且子代理的上下文不同（静默 OutputHandler、更短历史）⇒ 插件可能误判；storm 抑制/权限链与委派语义会互相干扰 |
| C | 白名单式：仅"显式声明要覆盖子代理"的钩子透传 | 精确、边界显式；代价：多一层声明机制 —— 而当前**只有权限链一个真实消费者**，与"不建声明层"的克制相冲突（第三圈触发条件同款判据）|

**影响**：A = 安全靠"白名单+沙箱"两条（且沙箱是可选项，见 §3）；B/C = 子代理受权限门约束，但插件语义复杂度上升。

## 2. 服务：子代理能不能看到父注册的能力（如 `referenceAnalysis`）？

**现状（证据）**
- 空宿主 ⇒ `host.get('referenceAnalysis')` 恒 `undefined` ⇒ 子代理内的引用分析走**核心兜底**（字符串扫描）。
  **实测证据**：`src/orchestrator/loop-reference-analysis.test.ts`（端到端，断言走兜底、结果与字符串扫描同源）。
- 但子代理**共享父的工具实例**（`delegate-tool.ts:243` `FilteredToolRegistry(parentContext.toolRegistry, …)`）
  ⇒ 进程内的结构事实（`file-tracker`：哪个文件刚被读/写）对子代理可见。

**选项**
| | 做法 | 代价 |
|---|---|---|
| A（现状）| 不共享 | 行为可预期、无跨 Agent 状态耦合；代价：子代理内只有兜底精度（精确清单/标注拿不到）|
| B | 共享父宿主 | 精确结果 ✓；代价：父卸载插件 ⇒ 子代理**中途失去能力**；"谁能看到什么"变成隐式的（谁在跑就有谁）|
| C | 显式传入**只读能力子集** | 精确 + 边界显式 ✓；代价：需要"服务分级"概念（当前不存在）|

**影响**：A = 精度让位于边界简单；B = 精度最高但耦合最深；C = 最好也最贵（要新增分级与透传规则）。

## 3. 权限升级：子代理内的权限请求怎么处理？

**现状（证据）**
- 自动批准：`delegate-tool.ts:314` `onPermissionRequest: async () => 'yes'`。
- 不过权限链（见 §1）。
- 现有缓解只有两条：工具白名单（`:243`）+ 路径沙箱（`:246-249`）。
  ⚠️ **关键空档**：沙箱**只在 `parentContext.sandboxRoot` 被设置时才生效**（`:246` 的 `if`）——
  未设置时，子代理可写**任意路径**（只要它的 `allowedTools` 里有 write/edit）。

**选项**
| | 做法 | 代价 |
|---|---|---|
| A | 接受现状 + 文档化（"白名单+沙箱代替权限门"）| 零改动；代价：默认配置下**无路径限制**（上条空档），最坏面是"子代理越界写文件" |
| B | 权限请求**升级到父**（冒泡给人审）| 语义最正确；代价：委派常是无人值守场景，父可能也被静默化 ⇒ 会卡住；且需要父子间的请求通道（当前无）|
| C | 默认收紧：`allowedTools` 默认不含 veto 类工具（rm/写类 bash）+ **默认**设置 `sandboxRoot`（= 父 cwd）| 零交互且封住最坏面；代价：依赖"子代理能跑 bash/写任意路径"的既有用例会变（需盘点）|

**影响**：A = 现状风险自担；B = 安全但破坏无人值守；C = 安全且零交互，但要盘点用例 + 改默认值（属行为变更）。

---

## 4. 实施方建议（仅供参考，非结论）

- **§3 先做 C 的"下半"**（默认设 `sandboxRoot` = 父 cwd）——它零交互、封住唯一无防护的面，
  且**不需要**回答"父子边界怎么设计"这个大问题；
- **§1 与 §2 一起决定**：它们共享同一个答案（"父 loop 的挂载物是否随委派传递"）——
  若决定 C（白名单/只读子集），两处都用同一套"显式子集"机制，避免各造一套；
- **A 永远是可接受的答案**，前提是 §3 的空档补上（否则"接受"二字没有对应防线）。
