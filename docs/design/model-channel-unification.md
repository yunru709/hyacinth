# 模型调用统一设计（厂商 / 通道 / 调用点）

> **状态：提案（待评审）** · 2026-10-01
> **目标读者**：维护本仓库的人与 Agent
> **本文只描述现状与方案，不含实现代码**；落地步骤见 §5。
> 文中每条"现状"都可在源码中核对，关键位置见附录 A。

---

## 0. 一句话概括问题

系统里**同一个问题（"用哪个模型"）有两套并存的答案**：一套决定主对话，另一套（通道）决定主对话之外的调用点。两套各有自己的配置文件、自己的命令、自己的默认值，并且**共用了一批名字**（`main` / `provider` / "主对话通道"）。

---

## 1. 设计意图（应有的形态）

原始设计目标：**让 provider 模块能给不同调用点输出不同模型** —— 例如压缩器用免费模型、旁路 Agent 用另一个免费模型、主对话用收费模型。为此引入"通道"这一层。

三层，自下而上：

| 层 | 职责 | 一句话 |
|---|---|---|
| **① 模型配置** | 有哪些厂商、各走什么协议、各提供哪些模型、每个模型的参数与字段映射 | "我们认识哪些模型" |
| **② 通道** | 一条"用哪个厂商的哪个模型"的绑定，附凭证、隔离标识、采样参数 | "一次具体的选用" |
| **③ 调用点绑定** | 谁（主对话、压缩器、旁路、子 Agent…）用哪条通道 | "谁在用" |

三条规则（**均为原始设计意图**）：

1. 一个调用点 → 一条通道；**多个调用点可共用一条通道**。
2. **多条通道可指向同一个模型**，用隔离标识（`userId`）区分各自的缓存。
3. **主对话只是调用点之一**，不特殊。

> 按此意图，"主对话"本应与压缩器、旁路平起平坐，由③统一指派。

## 2. 现状调查（代码事实）

### 2.1 三层的实际构成

| 层 | 实际存放 | 状态 |
|---|---|---|
| ① 模型配置 | `~/.agent/providers.json`（用户侧）+ 源码 `MODEL_CATALOG`（内置）+ `~/.agent/config.json` 的 `provider.<厂商>` 段 | **重复**：厂商端点/模型名在多处各存一份 |
| ② 通道 | `~/.agent/model-channels.json`（`channels` 表） | 存在，但只服务部分调用点 |
| ③ 调用点绑定 | 同文件的 `roles` 表 | 存在，但**主对话不在其中** |

### 2.2 数据流（现状）

```
主对话 ──→ loop.provider ──→ 由 config.json 的 provider.active 决定
                │
                │  （切换主 provider 时，单向推给通道的 main）
                ↓
        ModelRouter.setMainProvider()
                ↓
辅助角色 ──→ ModelChannelRegistry.getProvider(role) ──→ roles 表 → 通道 → 厂商/模型
             （compression / sub-agent / 旁路 / assessment / planning / orchestrator / narration）
```

**两条线互不相通**：切通道不影响主对话；切主对话会把通道的 main 顺手改掉（单向）。

### 2.3 调用点清单（实际使用通道的）

| 调用点 | 取值方式 | 位置 |
|---|---|---|
| 压缩器 | `createScopedProvider('compression', userId)`，失败回退 `getProvider('compression')` | 压缩器模块 |
| 子 Agent | `createScopedProvider('sub-agent', userId)` | 装配层 |
| 旁路 Agent | 按 role 取 provider | 旁路基类 |
| 评估 / 规划 / 编排 / 叙述 | 经 roles 表映射 | 角色表 |
| **主对话** | **不使用通道** | 走 `loop.provider` |

### 2.4 两套机制的四个交汇点（混乱的具体来源）

1. **`buildFromLegacy()`**：没有通道配置文件时，用 `provider.active`（缺省 `deepseek`）自动造出 main 通道，并写下备注 **"主对话通道（自动构建）"**。
2. **`mergeDefaults()`**：配置文件里缺 main 通道时，同样用 `provider.active` 补一个，备注 **"主对话通道"**。
3. **`ModelRouter.setMainProvider()`**：主 provider 切换时，把新的 provider **实例和类型**写进通道表的 main —— 但**不落盘**。
4. **`setChannelModel('main', …)`**：改通道 main 时，**同时**改写 `mainProvider` 引用 —— 于是两条线在内存里是**同一个对象**。

> 结论：main 通道**在代码里自称"主对话通道"，实际却不服务主对话**。这是命名与语义的直接冲突。

## 3. 问题清单

### P0 —— 会让人做出错误判断（已在 2026-10-01 实际发生）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | **切了通道，主对话不变** | 主对话走 `loop.provider`；通道 roles 表无"主对话" | 用户以为切了、实际没切（已实际发生一次） |
| 2 | **`list_providers` 一张表混两个维度** | 上半"声明层"是**厂商**，下半"实例层"填的是**通道名** | 看懂它需要先知道两套机制 |
| 3 | **报错文案误导** | `Available in router: main` —— `main` 是通道名 | 读起来像"只能选 main" |

### P1 —— 配置静默失效

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 4 | **主配置写着 `provider.active = openai`，但没有 OPENAI_API_KEY** | 启动时创建失败 → 静默回落到 deepseek | 配置意图与实际运行不符 |
| 5 | **通道配置四条通道全写成 `openai`**（main 甚至是已废弃的 `gpt-4o`），同样无 key | 日志每次启动一串 `Failed to create provider for channel …` | 四条通道全部创建失败，全靠回落 |
| 6 | **默认值腐化且无提示** | 通道配置是"某次自动构建"的产物，之后源码默认值更新不再回写 | 配置看着有、实际全是坏的 |

### P2 —— 结构冗余

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 7 | **厂商端点 / 模型名重复存放** | `providers.json`、`config.json` 的 `provider.<厂商>` 段、`model-channels.json` 三处 | 改一处不生效，难排查 |
| 8 | **老机制与新机制职责重叠** | `provider.active` 既决定主对话，又被 `buildFromLegacy` 用来造通道 | 两个真源 |
| 9 | **口径不一** | 通道注册表的 `getProviderType()` / `getModel()` 返回的是 main 的 | "当前模型"在不同入口含义不同 |
| 10 | **死文件** | `models-catalog.json` 无任何读取方（已于 2026-10-01 清除） | 误导维护者 |

## 4. 目标模型

### 4.1 单一真源，三层各管一件事

| 层 | 位置 | 谁维护 | 变更频率 |
|---|---|---|---|
| ① 模型配置 | `providers.json`（+ 源码内置目录兜底） | 基本由开发者/高级用户维护 | 低 |
| ② 通道 | `model-channels.json` 的 `channels` | 用户 | 中 |
| ③ 调用点绑定 | `model-channels.json` 的 `roles` | 用户 | 中 |

**关键变化**：把**主对话也登记为一个调用点**（例如 role `chat` 或 `primary`），指向一条通道。至此三条规则全部成立，`provider.active` 那套老机制退休。

### 4.2 配置归属（谁存什么，只存一份）

| 数据 | 唯一存放处 | 说明 |
|---|---|---|
| 厂商清单 / 协议 / 模型目录 / 字段映射 | `providers.json` | 用户侧覆盖，源码内置兜底 |
| API key | `.env`（按环境变量名引用） | 配置里只写变量名 |
| 通道 = 厂商 + 模型 + 凭证引用 + 隔离标识 + 采样 | `model-channels.json` | **不再**在 `config.json` 里重复厂商设置 |
| 谁用哪条通道 | `model-channels.json` 的 `roles` | 含主对话 |

### 4.3 命令统一

**目标**：所有"换模型"的操作，都从同一族命令走。

| 想做的事 | 命令 |
|---|---|
| 看有哪些通道、谁在用 | `/channel list` |
| 改某条通道用什么厂商/模型 | `/channel <通道名> model <厂商> [模型]` |
| 新建 / 删除通道 | `/channel add` / `/channel remove` |
| 把某个调用点指到某条通道 | `/channel bind <调用点> <通道名>` |
| **换主对话用哪条通道** | `/channel bind chat <通道名>`（即"换主对话"，不再是特殊的 `/model provider`） |
| 查看厂商清单 | `/provider list`（与通道清单**分开**） |

保留 `/model switch <模型名>` 作为"当前主对话通道换模型"的快捷方式（等价于改该通道的模型）。

### 4.4 显示与命名

1. **状态栏**：显示 `调用点 → 通道 → 厂商/模型`。主对话那行必须显式标注（它是**绑定到某条通道**的，不再显示成"另一个东西"）。
2. **`list_providers` 拆两张表**：厂商清单（声明层）/ 通道清单（含每个通道服务哪些调用点）。不再混排。
3. **通道名**：`main` 这种名字要么换掉，要么在输出里始终附带"服务哪些调用点"。
4. **报错文案**：区分"厂商名"与"通道名"两个词，报错时说明**你要的是哪个**。

## 5. 迁移步骤（每步可验证、可回滚）

> 原则：**主对话是命脉，任何一步都不能让它起不来。**

| 阶段 | 内容 | 验证方式 | 回滚 |
|---|---|---|---|
| **S1** | 把主对话登记为调用点（role `chat`），**默认指向它当前实际在用的厂商**；老机制继续生效（双读） | 启动后主对话仍正常；`/channel list` 能看到 chat 的绑定 | 删掉该 role 项 |
| **S2** | 主对话改为**从通道解析**（新路径），老 `provider.active` 保留为兜底 | 切换通道后主对话**确实改变**（此前不会） | 切回老路径 |
| **S3** | 清理配置：修正通道里的错默认值、移除 `config.json` 的 `provider.<厂商>` 段（先备份） | 启动日志**不再出现** `Failed to create provider` | 还原备份 |
| **S4** | 统一命令与显示（§4.3 / §4.4） | 手工过一遍命令表 | 单独回滚 |
| **S5** | 移除老机制残留代码 + 补守卫测试 | 测试全绿 + 分层门禁 | git revert |

**S1–S2 必须分两次提交**，且 S2 之前不允许删除老路径。

## 6. 风险与守卫

| 风险 | 守卫 |
|---|---|
| 主对话通道创建失败导致**起不来** | 通道解析失败必须**回落到老路径**（`loop.provider`），绝不可抛错中断启动 |
| 迁移中用户配置被破坏 | 每一步**先备份**（`.bak-<日期>-<原因>`）+ 改后回读校验 |
| 两条路径并存期间"双写"冲突 | 明确单向优先：**新路径优先，老路径只读兜底** |
| 用户已有配置被静默改写 | 只**补缺**，不覆盖用户显式值（沿用 2026-10-01 已落地的"逐字段回落"原则） |
| 判定"生效"靠错觉 | 交付前做**活体验证**（切一次、看真实生效值），不靠"读代码推断" |

## 7. 已定决策与遗留问题

### 7.1 用户已定调（2026-10-01 13:52）

1. ✅ **主对话有自己独立的通道** —— 不复用其它通道；新建主对话专属通道（命名 `chat`）。
2. ✅ **`main` 改名** —— 它误导（自称"主对话通道"却只服务角色）。改名为准确表达"默认通道"语义的名字（建议 `default`），**并对旧配置做兼容读取**（读到 `main` 自动映射，不可直接删键）。
3. ✅ **`provider.active` 彻底退役** —— 不再作为主对话的真源；连过渡期的"兜底"角色也一并移除。

> 落实顺序：改名与退役都涉及代码里多处硬编码 + 已落地的用户配置，**必须配兼容读取、分步提交**，不可一次删净。

### 7.2 仍待定（不阻塞推进）

4. **多租户隔离标识（`userId`）的暴露方式**：现在靠各调用点自己传（压缩器传 `hyacinth-compressor` 等），要不要统一到调用点绑定里配置？
5. **是否需要"通道继承/模板"**（如所有通道默认继承某条基础通道的凭证），以减少重复。
