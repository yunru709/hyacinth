# 工具联动三律（架构定律）

> 来源：《工具联动架构研究报告 v1.1》§1；2026-09-19 用户裁定为**长期有效**的行为准则。
> 本文件是**规范**，不是说明：凡新增工具间联动，一律按三律做，并按 §登记处 登记。

## 三律

### ① 工具永不 import 工具

机器化门禁：`npm run verify:layers` 规则 6（`scripts/tools-decoupling-whitelist.mjs`）。
共享逻辑抽成共享基础设施并登记进 `SHARED_TOOL_INFRA`；`KNOWN_TOOL_COUPLINGS` **空集是目标状态**。

### ② 跨工具的**结构事实**记共享账本，语义推导归订阅者

工具只负责把"发生了什么"（结构事实）记进共享基础设施，**不生产**下游语义。
先例：`diff-channel`（记 before/after 全文 —— Phase 6 为引用自检扩容）、`file-tracker`（记刚读/写过的文件）。
好处：上游只生产结构事实 ⇒ **几乎不可能因为"下游要什么"而改坏**。

### ③ 对工具行为的反应走钩子订阅，且订阅者失败不得影响宿主

机器化门禁：`src/kernel/hook-bus.test.ts`（观察者/拦截器抛错被吞并继续）。
注：**核心消费者**（如引用自检）不走钩子而直接内联在后置序列 —— 因为核心消费者要覆盖子代理
（子代理不接插件钩子），且兜底必须与插件有无无关。两者都合规：**"反应"不写进被联动工具本身**即满足本律。

## 新增一条联动的做法（准则，从此生效）

1. **只走干净缝**：订阅者（钩子）或能力注册（`ctx.register`）。**不建声明层**、**不改被联动的工具**。
2. 在生产侧登记"结构事实"（若有），消费侧自行推导语义。
3. **在锚点注释处同步登记**：源码里有六处 `[圈三锚点 · …]` 注释，标明第三圈接入时该动哪里；
   新增联动若改变了"能力/事件/展示"的形状，同步更新对应锚点旁的说明。

## 第三圈（联动清单 tool-links.json）

**触发条件（唯一）：第二个真实联动用例出现**（或"agent 自主接线"被确立为产品能力）。
在此之前**不实现**：清单本体、事件级联、项目级配置文件 —— 三者都属"0→1 个消费者就引入声明层"，
与 `tools-decoupling-whitelist` 那句"空集就是目标状态"是同一种克制。

触发后按研究报告 §3.3 实施（全局单层、加载即校验并保旧、防呆不防攻击、append/enrich 类 agent 可改、
veto/intercept 类架构所有）。

## 什么**不属于**本体系（判据，2026-09-19 用户裁定）

一句判据：**联动关心「工具做完之后发生什么」；前置条件关心「工具能不能做」**。

| | 属于联动 ✓ | 不属于（工具自身语义）✗ |
|---|---|---|
| 例子 | 改完自动更新依赖图（`incrementalUpdate`）／改完提示谁引用了它（引用自检）／改完跑诊断／权限链（策略来自外部）／路径沙箱（策略来自外部）| **read-before-write 门控**（`src/tools/read-gate.ts`）|
| 为什么 | 它给工具**加**了一个它本不需要的动作；事实来自别处，或被别处消费 | 它是这个工具**自身正确性**的一部分（"盲写"本身就是错的）——判定中没有第三方能力参与 |
| 因此 | 反应**不应写进**被联动工具（三律③）⇒ 适合做成消费者／订阅者 | 反应**必须**留在工具内（搬到外面反而让工具语义分散）——**三律③对它不适用** |

**推论**：`read-gate` **不搬进联动体系**（2026-09-19 一度计划迁移，被用户当场纠正）；
研究报告 §3.3 的 veto 类清单应**划掉 read-gate**，保留 `permission-chain` 与 `path-sandbox`
（后两者的**策略来自外部**，属联动）。

**顺带一条实操判据**：若某个反应"去掉之后工具会写出错误的东西" ⇒ 它是**前置条件** ✗；
若"去掉之后工具照常正确、只是少了一份帮助" ⇒ 它是**联动** ✓。
