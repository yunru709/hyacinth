# 密钥脱敏与还原（Secret Redaction / Restore）

> 2026-10-31 立项（**讨论/设计阶段，尚未实现**）。
> 触发：用户提出「用户消息里的密钥，发往云端模型前先替换为标记，云端只看到标记；模型处理完成（如把密钥写进文件）时，本地再把标记还原成真实密钥」——目标是避免明文密钥进入模型厂商服务器。
> 本文记录可行性、关键风险与分期方案，供后续实现参考。**尚未落代码。**

---

## 1. 动机

用户可能把 API Key 直接贴在对话里。明文随请求进入厂商服务器（日志、可能的训练面）。期望：密钥在**出站前**替换为标记，模型只见标记；真的要用它（写文件 / 调工具）时，本地再还原。

## 2. 现有底盘（可复用）

`src/kernel/security/env-guard.ts` 已有：

- `registerSecretKeys(keys)` —— 登记已知密钥**名**（`registeredSecretKeys: Set<string>`）
- `scrubEnv(env, opts)` —— 把密钥从**子进程环境**剥离（防泄进 `bash` 子进程），已生效
- `isSecretKeyName()` —— 名字是否匹配 `API_KEY|SECRET|PASSWORD|CREDENTIAL|PRIVATE_KEY`
- `ConfigManager`（`config.ts:464`）加载 `.env` 后调 `registerSecretKeys`，登记的是 **key 名**

**缺口**：只有名字、没有值；没有文本级脱敏；没有还原。

## 3. 判据（怎样才算"安全地做到了"）

1. 明文密钥**不出本机**——出站请求体里不出现
2. 标记**语义透明**——模型知道"这是敏感值，原样搬运，勿改写/截断"
3. 还原**只发生在安全出口**（不出网的：本地文件写入 / 本地命令 / 本地编辑）
4. 外发出口（`http_request` / `send_channel_message` / `curl` 等）**拒绝还原**并留审计
5. 还原能力**默认关闭**（高危场景由用户显式开启）

## 4. 设计

### 4.1 标记

`<secret id="s1" name="OPENAI_API_KEY"/>` —— `id` 是本次请求内的映射键，`name` 给模型可读语义。

### 4.2 出站脱敏（provider 请求前）

- 已登记密钥：需要 `keyName → value`（**要把 `registeredSecretKeys` 从 Set 扩成能拿到值**）→ 值级精确替换
- 未登记（用户新贴的）：模式识别（`sk-` / `ghp_` / `AKIA` / `xoxb-` / 高熵串）
- 挂点：context composer 组装完成 → provider 组装请求体之间（或 provider 适配器出口，一处收口）

### 4.3 入站还原（工具执行前）

- 工具参数含标记 → 还原成明文
- **出口白名单**：`write/edit/insert/本地 bash(无网络)` 允许还原；`http_request/send_channel_message/curl/wget` **拒绝**（阻断或告警 + 审计）

## 5. ⚠️ 核心风险：还原通道 = 密钥洗白机

还原机制等于**给模型一把"标记→明文"的开关**。一旦模型被提示注入 / 恶意工具返回诱导，把标记塞进**会出网的工具参数**（发消息、请求外部域名、`curl`），本地机械还原 ⇒ 密钥当场外泄。这比不做还危险——不做的话模型根本没见过真密钥。

因此 **§4.3 的出口白名单是成败关键，不是可选项**。做不好，就只做一期（出站脱敏），不给模型任何还原能力。

## 6. 局限（明确不承诺）

- 防不了：密钥写进文件后被 git / 日志 / 分享出去
- 防不了：模型在同一轮里**复述**明文（除非出站已经先脱敏）
- 新增风险：模型不理解标记 → 改写/截断 → 还原匹配失败 → 工具报错

## 7. 分期方案

| 期 | 范围 | 新增风险 | 结论 |
|---|---|---|---|
| **一期** | 出站脱敏 + WebUI 输入框「检测到疑似密钥，建议放 `.env`」提示 | **0**（无还原通道） | **建议做** |
| **二期** | 可逆还原 + 出口白名单 + 审计日志 | 高（洗白外泄） | 默认关闭，谨慎评估 |

一期≈80% 收益（密钥不上云）、≈20% 复杂度、零还原风险。二期本质是"把密钥的复制权交给云端模型"，收益（让模型代写密钥）低于风险——若确需自动化，优先考虑「涉密操作路由到本地模型（llama.cpp）处理、根本不上云」，比给云端模型发还原权更安全。

## 8. 实现时参考的钩子

| 环节 | 位置（预期） |
|---|---|
| 值登记 | `env-guard.ts`：`registeredSecretKeys` 扩展出 value，或新增 `secretValues: Map<name,value>` |
| 出站 redact | `context` 组装完成 → provider 请求前 |
| 入站 restore | `slot:tools` 工具执行器前 + 出口白名单判定 |
| UI 提示 | `webui` 输入框：疑似密钥模式检测 |
| 审计 | `kernel/security/audit.ts`（还原/拒绝事件落审计） |

---

## 9. 一句话结论

**先做一期（出站脱敏 + UI 提示），二期（还原）除非能保证出口白名单，否则不做。** 最好的安全是「让密钥走 `.env`、压根不进对话」——一期正好把这条兜住。
