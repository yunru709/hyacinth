## 1. 任务目标（为什么做这件事）

系统里"用哪个模型"有**两套并存的答案**：一套管主对话，一套（通道）管其余调用点。
两套各有配置文件、各有命令、且**共用名字**（`main` / "主对话通道"），导致用户切了通道却看不到变化。

**目标**：统一为单一真源三层 —— ①模型配置（厂商与模型目录）→ ②通道（一次具体选用）→ ③调用点绑定（谁用哪条）。
**核心动作**：把**主对话也登记为一个调用点**，让它和压缩器、旁路一样走通道。

## 4. 关键决策（执行者所定，接手者需知悉）

| # | 决策 | 理由 |
|---|---|---|
| 1 | 主对话调用点命名为 **`chat`** | 与既有 `compression`/`sub-agent` 同层级，语义直白 |
| 2 | `main` **通道名保留** | 它是"默认通道"（未绑定调用点的兜底）。改名会牵动已落地的用户配置与多处代码，收益不抵风险；改为**在显示层标注它服务哪些调用点** |
| 3 | `provider.active` **暂保留为兜底** | 主对话是命脉。通道解析失败时必须能回落，绝不能"配置写错就起不来"。是否彻底退役留到 S5 再议 |
| 4 | 通道解析**失败不抛错** | `ModelChannelRegistry.getProvider()` 内部已回落 `mainProvider`，该行为保留 |
